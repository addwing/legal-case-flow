# 使用

一句话：**一条流水线，七个工位，两处交接。** 你只需要记住「下一步该干什么」，
具体命令由 `flow.py next` 打出来，不要凭记忆敲。

---

## 心智模型

```
材料 ──▶ ① 事实底稿（F001 起编）
           │
           ├─▶ ② 法律关系图 ──┐
           ├─▶ ③ 庭审对抗图 ──┼─▶ ⑤ 课件（要讲才做）
           └─▶ ④ 时间轴 ──────┘
                    ⑥ 数据图（有一批判决才做）
                    ⑦ 重画（只接外部旧图）
```

规矩只有三条：

1. **① 永远在第一。** 后面的图都从它取事实与编号；反过来跑，等于同一批材料读两次。
2. **②③ 可以并行，也可以只做一个。** 缺哪个就跳过，`bind.py --plan` 会写明。
3. **④ 是旁路。** 只在「距离本身是论点」时才上——时效、逾期、期间重叠，或者要拿两方材料对读。

---

## 第 0 步：备材料

```bash
python3 <技能>/scripts/flow.py init 案件-某某诉某某 --title "某某诉某某合同纠纷"
```

它会摆出：

```
案件-某某诉某某/
├── 材料/                 ← 原样丢进去，不用先整理
└── 产物/
    ├── 大事记/  时间轴/  关系图/  对抗图/  课件/
```

材料怎么放：

- **支持**：PDF（含扫描件）、Word、图片、Excel、纯文本
- **不用改名、不用分类、不用先 OCR**。上游的读取层会自己抽
- **扫描件也照放**。区别只是「没有文字层」，取文字要多一步栅格化 + OCR
- **判决书、合同、证据目录、笔录、鉴定意见**这几类优先放，材料范围那一段靠它们填

---

## 第 1 步：事实底稿（`facts` 角色）

先问路：

```bash
python3 <技能>/scripts/flow.py next 案件-某某诉某某
```

它会打印**这一步该敲的完整命令**（带上绑定好的绝对路径）。照它跑。
上游那几家都有必须问人的环节（勾材料、勾时段、定风格），所以本层不替你一口气跑完。

**这一步的产物**（都在 `产物/大事记/`）：

| 文件 | 是什么 |
| --- | --- |
| `casefile.json` | 底稿。下游唯一的事实来源，`F001` 从这里开始编号 |
| `案件大事记.docx` | 给律师/法官看的交付版 |
| `大事记母表.xlsx` | 可筛选、可复核的母表 |
| `简表-P1.svg / -P2.svg` | A4 两页简表，可直接打印或放进证据目录 |
| `转写稿/` | 扫描件的文字转写，逐页对应 |
| `sources.json` | 每条事实的出处索引 |

**验收三问**（不过就别往下走）：

1. 每条事实都有 `mid`（材料）与 `locator`（页码）吗？
2. 编号是连续的 `F001…F0NN`，没有跳号、没有重号吗？
3. 不确定的地方，是写进 `uncertainties` 了，还是被悄悄抹平了？

> 底稿 `content` 是照录原文。**不要在这一步写法律评价**——评价属于第 3 步，写进来就污染了事实层。

---

## 第 2 步：两处机械转接

只有这两件事能机械做，其余都是判断：

```bash
# ① → ③ 庭审对抗图的输入骨架，另出一份《事实挂载表》
python3 <技能>/scripts/handoff.py matrix 产物/大事记/casefile.json \
        -o 产物/对抗图/matrix-input.json \
        --index 产物/对抗图/事实挂载表.md

# ① → ② 法律关系图的输入（只出主体，一条关系都不生成）
python3 <技能>/scripts/handoff.py relations 产物/大事记/casefile.json \
        -o 产物/关系图/relations.json
```

两份产物都是**骨架，不能直接出图**。脚本会把待办逐条列出来，例如：

```
□ case.stance：我代理谁（原告向 / 被告向）—— 必须问律师，底稿推不出来
□ edges 一条都没有 —— 关系名与指向必须照录原文，脚本猜不出来
```

《事实挂载表》是给人看的：每条 `F` 编号 + 日期 + 证据 + 出处 + 原文，
填要件的时候照着挂，不用回翻卷宗。

---

## 第 3 步：结构层（`structure` / `adversary`）

**法律关系图**回答「谁与谁、就哪份合同、成立什么关系」：

- 填 `relations.json`：主体照录底稿 `parties`，关系名与指向照录原文
- 上限是 **9 个模块、12 条关系**，超了要先取舍
- 先 `--plan-only` 过规模判断，再出图

**庭审对抗图**回答「争点怎么打」：

- 填 `matrix-input.json`：立场、程序、成熟度、诉请、请求权基础与要件四段攻防
- 四段正文**照录**，条号案号**不编造**
- 17 列分析表是对内的推演稿，**不对法院出示**

两张图能并行。想先看结构就先做关系图，想先定攻防就先做对抗图。

---

## 第 4 步：时间轴（`chronology`，按需）

什么时候值得做：

- 争点是**时效**（起算点、中断、中止）
- 争点是**逾期**（交货、验收、付款、上诉期）
- 两方材料**对读**时有期间重叠或矛盾

什么时候不值得：单纯「把事实按时间排一遍」——那是大事记的活，再画一遍是重复劳动。

时间轴会自带 `-trace.json`（每个点能回溯到某条事实），这是它比大事记简表强的地方。

---

## 第 5 步：表达层（`deck` / `data`，需要才做）

- **课件**：要讲、要汇报、要交客户时才做。它只认 `assets/` 里的 `*.svg` 与同名 `-trace.json`；
  缺 trace 的图也能放，但悬停看不出处，讲的时候要口头补
- **数据图**：类案研究、判决结果构成、审理天数这类，要有**一批判决或逐件登记表**才上；
  单案一般用不上

---

## 第 6 步：交付前自检

出交付物之前，逐条过一遍：

- [ ] 每个图里的数字，能不能从底稿或输入 JSON 推出来？（推不出来的删掉）
- [ ] 每张图有没有 `-trace.json`？没有的话，讲稿里要能说清出处
- [ ] 分析表里的「结论」有没有混进正式文书？（对内推演稿不对法院出示）
- [ ] 时效/管辖/主体这类程序问题，有没有单独一段说清？
- [ ] 当事人姓名、案号、金额，与卷宗对得上吗？
- [ ] 要递交的那份，是不是**另起了一份正式文书**，而不是把分析稿改个名？

---

## 一条真实节奏：一审败诉，争二审

以加工合同纠纷、一审以时效届满驳回为例，这套东西一般这么排：

| 阶段 | 上什么 | 为什么 |
| --- | --- | --- |
| 拿到判决书当天 | ① 事实底稿 | 22 条事实、13 条不确定项，先把「什么是确定的」钉住 |
| 次日 | ③ 庭审对抗图 | 争点只有两个：起算点、有无中断。一张图摆清攻防 |
| 同周 | ④ 时间轴 | 时效案必上：起算点三个版本（合同约定 / 法定 / 实际履行）画在同一条轴上，矛盾自己会说话 |
| 定稿前 | ② 法律关系图 | 加工合同 vs 买卖合同的定性会牵动请求权基础，值得单独画一张 |
| 交客户 | ⑤ 课件 | 把「为什么一审错了」讲给当事人听，比给他看二十页代理词有效 |
| 不上 | ⑥ 数据图 | 单案，没有一批判决可统计 |

**改动的传播**：手机灭失这类新事实进来，只需改 ① 的两条注记 + ③ 的一个中心卡，
其余各层引用的编号不变。这就是「① 固定编号」的价值。

---

## 中断与恢复

任何一步都可以停。恢复时不要凭记忆：

```bash
python3 <技能>/scripts/flow.py next 案件目录
```

它按目录里已有的产物判断走到哪一步、缺哪个文件。换机器、换会话、换 agent 都一样——
所有中间产物都是普通文件，没有隐藏状态。
